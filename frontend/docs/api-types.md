# Generated API Types

The frontend's API types are generated from the backend's OpenAPI schema. This
eliminates hand-maintained DTO drift (role enums, `emergency_contact`, AI
explanation shapes) by making the compiler, not review, catch mismatches.

## Layout

| Path | Owner | Purpose |
| --- | --- | --- |
| `frontend/openapi.json` | committed | Snapshot of the backend OpenAPI schema (197 paths, 111 schemas) |
| `frontend/src/api/generated/**` | **generated, never edit** | Orval output: types + typed TanStack Query hooks |
| `frontend/src/api/mutator.ts` | hand-written | Routes generated calls through the existing Axios instance |
| `frontend/src/api/index.ts` | hand-written | Public facade — application code imports only from here |
| `backend/scripts/export_openapi.py` | hand-written | Regenerates `openapi.json` from the FastAPI app |

Generated files carry a `Generated by orval ... Do not edit manually.` header.
Any edit there is lost on the next run.

## Commands

```bash
npm run generate:api          # regenerate types from the committed openapi.json (no backend needed)
npm run generate:api:fetch    # fetch a FRESH schema from a running backend, then generate
npm run generate:api:check    # CI guard: fail if generated code is out of date
npm run verify                # check + typecheck + lint
```

Backend-side schema export (no running server required):

```bash
cd backend && python scripts/export_openapi.py
```

## When to regenerate

Regenerate whenever the backend API changes — a new endpoint, a renamed field, a
changed enum, a widened request body. Nothing in the frontend breaks silently:
a schema change that invalidates existing frontend code shows up as a
`npm run typecheck` failure.

Typical loop when working against a live backend:

```bash
# terminal 1
cd backend && uvicorn app.main:app --reload --port 8000

# terminal 2
cd frontend
npm run generate:api:fetch   # refresh openapi.json + regenerate types
npm run typecheck
```

Commit both `openapi.json` and `src/api/generated/**` together. The committed
schema is what makes codegen reproducible in CI and offline.

## CI

`npm run generate:api:check` regenerates into a throwaway directory and diffs it
against the committed output. Any drift fails the build, so the types in the repo
always match the committed schema. Add it to CI before `npm run typecheck`.

## Using the generated client

Import from `@/api` (or the equivalent relative path), never from
`src/api/generated/**` directly:

```ts
import { useGetCurrentUserProfileApiV1UsersMeGet, type UserResponse } from '@/api'
```

Three layers are generated per operation:

```ts
// 1. Plain typed function - use inside an existing service module
const user: UserResponse = await getCurrentUserProfileApiV1UsersMeGet()

// 2. TanStack Query hook - use in a component
const { data: user, isLoading } = useGetCurrentUserProfileApiV1UsersMeGet()

// 3. Query key / options factories - use for manual caching or prefetching
queryClient.setQueryData(getGetCurrentUserProfileApiV1UsersMeGetQueryKey(), user)
```

### Existing Axios instance is preserved

Generated calls route through `src/api/mutator.ts` → `src/lib/api.ts`, so the
shared instance keeps owning:

- the Firebase ID token request interceptor,
- the 401 refresh-and-retry-once response interceptor,
- base URL resolution (dev `http://localhost:8000`, prod relative `/api/v1`).

No generated code creates its own Axios instance. The mutator also strips the
`/api/v1` prefix that OpenAPI paths carry, because the shared `baseURL` already
ends in `/api/v1` — repeating it caused a real double-prefix bug in `cmsApi.ts`
previously.

Query keys still follow existing conventions. Migrate a feature by keeping its
current key array and swapping only the fetch function:

```ts
// before
useQuery({ queryKey: ['profile'], queryFn: fetchMyProfile })

// after - same key, no cache invalidation churn
useQuery({
  queryKey: ['profile'],
  queryFn: () => getMyProfileApiV1ProfilesMeGet(),
})
```

## Migrated reference examples

- `src/features/profile/api/profileService.ts` — payload typed from
  `PersonalInfoDTO`. The old hand-written interface typed `emergency_contact` as
  `string`; the backend stores an object, so that shape would 422 on submit.
- `src/features/auth/hooks/useAuthService.ts` — returns the generated
  `UserResponse`, whose `roles` is `string[]` rather than a narrow literal.
- `src/features/dashboard/api/patientService.ts` — AI explanation types
  (`AIExplanation`, `KeyFinding`, `RetrievedEvidenceContext`, ...) now alias the
  generated models under their old local names, so components import unchanged.

## Known drift still to migrate

These remain hand-written and are **not** typechecked against the schema yet.
Treat them as future migration work, not as verified-correct types.

| File | Issue |
| --- | --- |
| `src/features/dashboard/types/index.ts` | `PersonalInfo.emergency_contact?: string` — backend sends an object |
| `src/features/profile/api/profileApi.ts` | `emergency_contact` typed as `string` |
| `src/features/profile/api/profileService.ts` | now fixed (uses `PersonalInfoDTO`) |
| `src/features/profile/types/profile.ts` | `HealthProfile` lacks `lifestyle` / `nutrition`, which `ProfileSections.tsx` reads |
| `src/features/questionnaire/api/intakeService.ts` | Phase 3/5 intake types duplicated by hand |
| `src/features/interop/api/interopService.ts` | Phase 10 FHIR/SDG/referral types duplicated by hand |
| `src/features/health-timeline/api/trajectoryService.ts` | Phase 4 trajectory types duplicated by hand |
| `src/features/analytics/api/analyticsApi.ts` | Phase 6 analytics types duplicated by hand |
| `src/features/cms/types/**` | CMS entity types duplicated by hand |
| `src/types/role.ts` | Role/permission union — intentionally hand-written; roles are RBAC config, not an OpenAPI enum, so keep this |

`fetchMyProfile` in `features/profile/api/profileService.ts` intentionally keeps
its previous loose return type: `ProfileSections.tsx` reads `profile.nutrition`
and passes `personal_info` into a lifestyle form, neither of which the backend
`HealthProfileDTO` exposes. Narrowing that return type would break working UI,
so it is left for a separate fix rather than bundled into the codegen setup.
